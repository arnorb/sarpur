# S2.1 status

## Slice 1 (branch `s2.1-core`): the core download path

A running `sarpur` server takes one RÚV episode through queue → worker → ffmpeg → `.part` → final name, in library and browser modes, with its state in SQLite.

- **Workspace:** `crates/sarpur-lib` (modules `config`, `settings`, `db`, `worker`, `catalogue`, `library`, `media`, `jobs`) and `crates/sarpur` (the axum server and CLI).
- **CLI:** `sarpur [--bind 127.0.0.1] [--port 8090] [--data-dir DIR] [--dry-run]`. Environment: `SARPUR_DATA_DIR`, `SARPUR_PYTHON` (default `python3`), `SARPUR_WORKER` (default: the first `worker/ruvsarpur.py` in the executable's folder or a parent, else the repo it was built from), `SARPUR_FFMPEG` (default `ffmpeg`), `RUST_LOG`. On unix the server sets `umask 002`.
- **Worker:** one `python ruvsarpur.py --json --portable <command>` per call, run in the data folder, with a timeout per command. New `plan` command returns the name, content type, playlist, duration and the exact ffmpeg metadata; the metadata comes from `buildFfmpegMetadata`, shared with the old download path. `resolve` and `plan` no longer use the dead `getProgramType` lookup.
- **Database:** `settings`, `jobs`, `recorded`, `library`; WAL, foreign keys, migrations by `user_version`; all access on the blocking pool.
- **Queue:** one ffmpeg at a time, interactive before scheduled, FIFO within a priority. Startup recovery deletes leftover `.part` files, requeues interactive jobs and fails scheduled ones with "interrupted". Disk-space check (2× the estimate). Cancel sends `q`, kills after 10 s, deletes the `.part`. SIGTERM or Ctrl-C stops ffmpeg and leaves the job for recovery.
- **Library rule:** an explicit Library download completes as "Already in the library" when a file matches the expected name as a prefix (`<name>*.mp4`, compared literally so `[`/`*`/`?` are safe). Library jobs record the pid as origin `library` (and a `library` row); browser jobs only ever write origin `web`.
- **Browser downloads:** `<data>/web/<job>/<name>`, served at `/api/jobs/{id}/files/{name}`, swept after 24 h (at startup and hourly).
- **Catalogue:** kept in memory, loaded from the worker at startup (in the background) and after `POST /api/catalogue/refresh`; substring search.
- **API:** see `docs/api.md`. SSE job updates to everyone, `file_ready` only to the matching `client_id`.

On a fresh data folder there is no `tvschedule.json`, so the startup load reports `failed` until `POST /api/catalogue/refresh` has run once.
